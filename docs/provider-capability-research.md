# Provider capability research (26–30 September 2026)

This note turns current provider and platform documentation into *candidate* Aistee work. The maintained product backlog is [product-ideas.md](product-ideas.md); existing transport and state rules are in [provider-runtime.md](provider-runtime.md). It does not claim that an account-backed WebView exposes an API feature or that ordinary subscription access automatically includes API usage. The OpenAI subscription-backed runtime update was checked against `main` at `3754a55` on 30 September 2026; older provider/APK findings below retain their original research context.

### Provider-specific decisions

- **Microsoft Copilot:** keep the existing consumer/account Copilot WebView. Microsoft 365 Copilot Chat API is a *different*, preview, Graph-based enterprise integration requiring a Microsoft 365 Copilot add-on license per user. It offers text and SSE, with no file creation or long-running tool jobs in the documented API. Do not add it to the free/native provider picker or reuse consumer WebView credentials. Revisit only if an actual licensed organizational use case appears. [Microsoft Learn: Chat API overview](https://learn.microsoft.com/microsoft-365/copilot/extensibility/api/ai-services/chat/overview), [Copilot APIs overview](https://learn.microsoft.com/microsoft-365/copilot/extensibility/copilot-apis-overview).
- **Grok:** keep Grok Web, xAI developer API, SuperGrok and Grok Bot separate. The direct native path should use its own xAI API key/billing and live model catalog rather than reuse consumer cookies or make a gateway the only Grok route. xAI's own Chat Completions docs call that endpoint the predecessor of Responses for new integrations; Responses exposes richer provider tools, while exact model/tool support still needs capability checks. Files remain until deletion unless `expires_after` is set, so any future attachment path needs provider file IDs, expiry and explicit cleanup. [xAI Responses](https://docs.x.ai/developers/rest-api-reference/inference/responses), [xAI models](https://docs.x.ai/developers/rest-api-reference/inference/models), [xAI file lifecycle](https://docs.x.ai/developers/files/managing-files).
- **Grok Bot mobile APK:** the uploaded `ai.x.grok.bot` 1.12.0 has its own `x.ai/bot/...` deep links and a `text/plain` share target. These are distinct from Grok Web and xAI's developer API; they do not verify embedded login, model-tool access or a stable third-party bot integration. Static APK findings are recorded in [product-ideas.md](product-ideas.md#follow-up-grok-bot-microsoft-copilot-and-chatgpt-apks-26-september-2026).
- **Official Grok mobile APK:** the newly supplied `ai.x.grok` 1.2.39-release.02 is the main Grok client. It registers broad share, selected-text, voice and four widget entry points, and its resources also mention Grok Bot; that association does not turn either mobile APK into the Grok Web session or the xAI developer API. See the [APK follow-up](product-ideas.md#follow-up-official-grok-mistral-meta-ai-and-manus-apks-26-september-2026).
- **OpenAI, Claude, Gemini:** #285 already implements OpenAI Background jobs; extend its existing job store if another provider gets a real async API. For repeated large project instructions, benchmark provider-specific caching only after measuring tokens and latency; avoid a cross-provider "cache on" switch with invented savings. [OpenAI background](https://developers.openai.com/api/docs/guides/background), [Claude prompt caching](https://platform.claude.com/docs/en/build-with-claude/prompt-caching), [Gemini context caching](https://ai.google.dev/gemini-api/docs/caching).

### xAI / Grok direct-runtime research (30 September 2026)

- **Responses-first is the useful direct integration.** xAI documents `/v1/chat/completions` as the stateless OpenAI-compatible predecessor and recommends Responses for new integrations. The direct Aistee adapter should therefore be a real provider implementation, not just an OpenAI-compat URL swap. Current xAI Responses/tool docs expose provider-side Web Search, X Search and code execution/interpreter plus client functions; the exact tool set can vary by API surface/model, so Aistee should discover/declare capabilities rather than infer them from the base URL. [Chat Completions](https://docs.x.ai/developers/rest-api-reference/inference/chat-completions), [Responses](https://docs.x.ai/developers/rest-api-reference/inference/responses), [tool output/streaming](https://docs.x.ai/developers/tools/streaming-and-sync).
- **Do not hardcode a Grok marketing model.** `GET /v1/models` lists models available to the authenticating key with identifiers, aliases, context/pricing metadata; xAI's public docs have already moved beyond the `grok-4.6` name cited in earlier notes. Direct Aistee should refresh this catalog and keep a safe fallback only for temporary discovery failure. [Models API](https://docs.x.ai/developers/rest-api-reference/inference/models).
- **SuperGrok is not xAI API billing.** Consumer Grok/SuperGrok uses its own subscription/weekly allowance, while developer API quickstart requires an xAI Console account, API key and API credits/invoiced spend. No current official third-party “spend my SuperGrok allowance through this client” contract was found. UI must therefore label Grok Web/SuperGrok and xAI API-key runs as different funding sources. [Grok FAQ](https://docs.x.ai/grok/faq), [API quickstart](https://docs.x.ai/developers/quickstart), [API billing](https://docs.x.ai/console/billing).
- **Files need lifecycle ownership.** xAI uploads can be permanent until explicitly deleted or can receive `expires_after` from one hour to 30 days. Aistee should default ephemeral chat attachments toward bounded retention, remember remote file IDs and offer/best-effort perform delete cleanup. [Managing files](https://docs.x.ai/developers/files/managing-files), [delete file](https://docs.x.ai/developers/rest-api-reference/files/manage).
- **Token Arena can use xAI's tokenizer, with a caveat.** `POST /v1/tokenize-text` returns model token IDs for supplied text and belongs in its own xAI/model series. xAI also documents that inference adds predefined tokens, so this count can differ from actual prompt-token consumption. Treat it as provider-native text tokenization, not a full assembled-request/billing count, and never blend it with `o200k_base`. [tokenize-text](https://docs.x.ai/developers/rest-api-reference/inference/other), [billing FAQ](https://docs.x.ai/developers/faq/billing).
- **Deferred Chat Completions are job-shaped but not equivalent to Aistee's existing batches/background jobs.** xAI returns a request ID; the result is available for retrieval exactly once within 24 hours. Model its TTL/retrieval semantics before wiring it into Jobs and do not imply batch discounts. [Deferred Chat Completions](https://docs.x.ai/developers/advanced-api-usage/deferred-chat-completions).
- **Imagine and Voice are separate capability families.** xAI exposes dedicated image/video and voice APIs/model catalogs. Put Grok Imagine outputs into the common media/artifact flow and keep voice under shared realtime/audio surfaces instead of stuffing either into the text-model provider list. [Imagine](https://docs.x.ai/developers/model-capabilities/imagine), [models](https://docs.x.ai/developers/models).
- **Grok Bot is another product boundary.** xAI now documents Grok Bot as a persistent cloud-computer teammate included with some Cursor plans and linkable to paid SuperGrok plans. That makes it interesting for Agent Lab handoff research, but does not make Grok Bot's app/deep links an xAI inference API or a Grok Web session bridge. [Grok Bot](https://docs.x.ai/grok-bot/overview).

### OpenAI subscription-backed runtime research (30 September 2026)

- **Sign in with ChatGPT is the direct match for the Aistee idea.** OpenAI now documents optional ChatGPT-plan usage for open-source and locally hosted apps: eligible ChatGPT Plus/Pro users can authorize an app to make eligible Responses API requests against their plan/available credits without supplying an API key. The permission is separate from identity sign-in, does not expose ChatGPT conversations, and uses OAuth/PKCE plus a provider-issued client registration. For the OSS flow, first-time registration uses `dynamic_agent_client` plus a stable per-host `ext_agent_host_id`; the issued `client_id` is bound to the selected user/workspace, and the flow needs neither a client secret nor a partner API key. This makes a custom Aistee-native chat funded by the user's ChatGPT plan a concrete planned integration rather than a speculative WebView trick. [Quickstart](https://developers.openai.com/siwc/quickstart), [open-source plan usage](https://developers.openai.com/siwc/token-sharing-open-source), [registration/sign-in](https://developers.openai.com/siwc/token-sharing-open-source/sign-in), [cookbook example](https://developers.openai.com/cookbook/articles/sign-in-with-chatgpt).
- **The account-plan model catalog is account-specific.** OpenAI's OSS guide says to call `GET /v1/models` with the same OAuth access token used for Responses, keep entries intended for display and pass the returned model slug into inference. Aistee should therefore discover models per connected ChatGPT account/workspace instead of assuming the API-key catalog or a static marketing list. [Models and inference](https://developers.openai.com/siwc/token-sharing-open-source/models-and-inference).
- **The plan-backed Responses route is not full API parity.** Current preview requirements include `store=false`, streaming and explicit client-managed history. Function/custom tools are supported, but image generation, file search, Code Interpreter, native computer use, hosted MCP/connectors and Responses tool search are currently unsupported. Aistee must therefore resolve features by auth/runtime capability instead of assuming the API-key adapter can be replayed unchanged. [Preview limitations](https://developers.openai.com/siwc/token-sharing-open-source/preview-limitations).
- **Image generation is real, but currently API-key-funded for the desired native flow.** OpenAI's API supports `gpt-image-2.5-sunburst` and `gpt-image-2.5-flare` through the Image API and as the Responses image-generation tool. The exact UX proposed for Aistee—type a normal image prompt and receive an artifact—is straightforward on the API-key route, while direct ChatGPT-plan-backed image generation remains blocked by the current Sign in with ChatGPT preview tool restrictions. [Image generation](https://developers.openai.com/api/docs/guides/image-generation).
- **Codex proves the broader product pattern.** OpenAI officially supports ChatGPT sign-in for Codex clients and charges that usage against the ChatGPT plan/allowance; API-key authentication instead uses API pricing. This is evidence that subscription-backed runtimes outside the default ChatGPT chat are an intentional product pattern, but it is capability-specific and does not imply a universal consumer-account API token. [ChatGPT Work and Codex](https://help.openai.com/en/articles/20001275), [Codex authentication](https://learn.chatgpt.com/docs/auth).
- **ChatKit fits as a UI/runtime reference, not as the subscription bridge.** ChatKit provides customizable chat UI, widgets, attachments, tool invocation and actions, and its advanced mode can connect to a custom server-side agent. The hosted/session examples still use server-side OpenAI API credentials, so Aistee should not treat ChatKit as a way to spend a ChatGPT subscription. Its custom-server path can nevertheless sit in front of an Aistee-owned runtime router, so a future web/desktop shell could render ChatKit while a separately authorized Sign in with ChatGPT token funds eligible Responses requests behind it. The auth token remains a runtime concern, not a ChatKit credential. Agent Builder's hosted path is being retired on 30 November 2026 while ChatKit remains, which makes the custom-server path the relevant reference. Native Compose remains the better default Android shell; borrow ChatKit interaction patterns or use it only where an embedded web surface earns its complexity. [ChatKit](https://developers.openai.com/api/docs/guides/chatkit), [custom ChatKit](https://developers.openai.com/api/docs/guides/custom-chatkit).
- **Billing remains explicit.** Ordinary ChatGPT subscriptions and API Platform billing remain separate; only documented plan-usage integrations bridge that boundary. UI must state which funding source is active and must never silently fail over from plan usage to a paid API key. [OpenAI billing](https://help.openai.com/en/articles/9039756-managing-billing-settings-on-the-chatgpt-web-and-api-platform).

## Before implementation

Keep the existing WebView verification lane, but treat official native runtimes as independent lanes rather than waiting for every Web provider check. For OpenAI, keep the existing one-PR-per-slice sequence: (a) ChatGPT-plan auth/profile storage plus a minimal Responses request, (b) capability-driven request differences and usage UI, (c) selected-library context and source provenance, (d) typed Docbench export, (e) tool-call receipts. For xAI, start separately with direct key storage + live model discovery + a minimal Responses request, then add provider tools, file lifecycle, Token Arena tokenizer and media/jobs as independent slices. Verify current model support, cost, retention and AndroidX feature availability at implementation time. No new Aistee account, consumer-cookie bridge, hosted backend, remote skill execution or duplicate `.ai` configuration is implied by this research.
